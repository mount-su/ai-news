# AI 日报候选口径均衡放宽规格

## 背景

近期回放显示采集器本身可以拿到大量原始内容，但进入日报的候选很少。主要原因不是来源失效，而是现有编辑链路同时使用了 36 小时时间窗口、30 天历史 URL 去重、确定性编辑过滤和 LLM 严格提示词。其中确定性规则和提示词仍按“普通用户/业务价值优先”阶段设计，几乎整体排除了 SDK/API、框架、代码工具、benchmark 和技术发布。

用户已确认新的口径：技术文章可以进入日报，但不能低质、细碎或偏科研学术。目标是在不牺牲可读性的前提下，让日报稳定覆盖更多值得关注的 AI 产品、模型、应用、开发生态和产业变化。

## 已确认决策

1. 采用方案 B：均衡放宽。
2. 时间窗口从 36 小时扩大到 72 小时。
3. 30 天历史 URL 去重保持不变，避免扩窗后重复刷旧内容。
4. 允许高质量技术内容入选，但仍拒绝纯科研论文、学术细节、弱 benchmark、小版本修复、泛教程和缺少事实支撑的营销内容。
5. LLM 继续承担主编取舍，不为凑数保留弱内容。
6. 本次不新增数据源、不改变页面样式、不改变 GitHub Pages/Actions 架构。

## 内容准入规则

### 应保留

以下技术或产品内容可以进入 LLM 候选池：

- 重要模型能力、模型可用范围、价格或调用成本变化；
- 主流 AI 产品、Agent、AI 应用或企业部署的实质更新；
- 重要开源项目的重大版本、架构变化、破坏性变更或生态影响；
- 直接影响开发者或企业采用的 API/SDK/平台变化，例如成本、性能、稳定性、兼容性或访问门槛变化；
- 安全漏洞、服务中断、合规限制、平台政策和可执行迁移事项；
- 有明确生产落地、用户规模、商业影响或可验证行动价值的技术文章。

### 应拒绝

以下内容仍应在确定性过滤或 LLM 主编阶段排除：

- 纯论文、科研项目、arXiv 摘要、模型原理细节和偏学术综述；
- 只有 benchmark 或排行榜、但没有产品化、成本、性能或采用影响的内容；
- 小版本、补丁、连接器修复、参数调整、普通 changelog 和内部实现细节；
- 泛教程、模板文章、SEO 内容、观点复述和没有新事实的营销稿；
- 融资、人事、估值、收购等公司新闻，除非候选事实明确改变产品、市场或用户可用性；
- 只能总结成“具有重要意义”“提供参考”的弱内容。

## 生成流程调整

### 时间窗口

`src/ai_news/pipeline/run.py` 的采集窗口改为 72 小时。窗口边界仍沿用现有语义：`now - window <= published_at <= now`。未来时间、历史 URL 和无效候选继续被排除。

### 确定性编辑过滤

`src/ai_news/pipeline/editorial.py` 保留低质技术和纯公司新闻的拒绝逻辑，但拆分技术信号：

- 学术/论文/科研信号默认拒绝；
- 低价值发布信号默认拒绝；
- SDK/API/框架/代码工具不再一刀切拒绝，只有缺少高影响信号时拒绝；
- 高影响信号扩展到成本、性能、稳定性、生产部署、广泛采用、破坏性变更、安全、可用范围和主流产品发布。

### LLM 主编提示词

`src/ai_news/llm/prompt.py` 需要和新口径一致：

- 移除“SDK/API、开发框架、代码工具必须排除”的绝对表述；
- 改成“只有高质量、可执行、影响明确的技术内容才可保留”；
- 明确拒绝纯学术、弱 benchmark、小版本修复、泛教程和营销内容；
- 保持最多 9 条、单一来源最多 3 条、不强行凑数、同一事件去重和字段约束。

## 数据与展示

本次不改变报告 schema、站点模板、分类枚举或历史兼容策略。最终日报仍最多 9 条，`candidate_count` 继续表示进入 LLM 的候选数量，不代表原始抓取总量。

预期效果是普通日期的候选池比当前更宽，尤其是过去 72 小时内的高质量技术发布不会因为 36 小时窗口或旧提示词被过早排除。但数量不是硬指标：如果某天确实没有高价值内容，仍允许少量发布或保留上一期。

## 测试与验证

### 自动化测试

- 增加编辑过滤测试，证明高影响 SDK/API、框架、开源项目、性能/成本/生产部署内容可以通过；
- 增加编辑过滤测试，证明纯论文、弱 benchmark、小版本修复、泛教程和低质 changelog 仍被拒绝；
- 更新流水线窗口测试，覆盖 72 小时边界，并保留未来内容排除；
- 更新提示词测试，确认没有绝对排除 SDK/API/框架/代码工具，且保留“不凑数”和低质内容拒绝规则；
- 完整运行测试、覆盖率、Ruff、格式检查和密钥扫描。

### 数据回放

用当前代码和同一配置回放 2026-08-20、2026-08-21、2026-08-22。验收重点：

- 采集源无大面积失败；
- 候选数量较旧口径不减少；
- 新增候选符合“高影响技术或产品价值”口径；
- 最终日报仍保持精炼，不出现纯论文、低质小版本或泛教程。

## 发布策略

在独立分支完成改造并验证后提交 PR。合并后可通过现有 GitHub Actions 手动回放过去几天，再由 GitHub Pages 发布。若回放发现 LLM 仍过严或过松，应先调整提示词和确定性测试，再重新生成内容。
