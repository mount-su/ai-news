# AI 情报雷达精炼主编设计

## 背景

当前日报虽然能稳定采集、分析和发布，但最终页面不是有效的每日决策简报：

- 每期发布 20 条，单条同时展示长摘要、价值、标签、元数据和跟踪信号，阅读负担过重。
- 前三条在“今日最重要”和下方情报流中重复出现。
- 2026-07-30 的 20 条内容中有 18 条来自 arXiv，单一来源占比达到 90%。
- LLM 目前被要求逐条分析所有候选，没有承担跨来源比较、取舍和合并同一事件的主编职责。
- 重要性分数集中，首页首屏主要用于标题和采集统计，真正重要的内容出现在首屏之后。

本次改造的目标不是增加更多功能，而是把现有日报变成可在 3–5 分钟内读完、每天稳定提供 9 条高价值变化的精炼情报产品。

## 已确认的产品决策

1. 每期必须发布 9 条，不多不少。
2. 内容同时覆盖三个编辑方向：
   - 产品工程
   - 商业趋势
   - 前沿研究
3. 三个方向动态竞争，不固定为各 3 条；每个方向至少 1 条、最多 4 条。
4. 最终单一信息源最多出现 3 条。
5. 程序负责确定性清洗、去重、时效过滤和约束校验；LLM 负责跨候选比较、筛选、排序和精炼表达。
6. 页面不再重复展示前三条，也不再默认展示冗长的分析字段。
7. 每条内容只回答三个问题：
   - 发生了什么
   - 为什么值得关注
   - 建议关注或采取什么行动

## 生成架构

### 1. 采集与确定性预处理

保留现有 15 个信息源和采集器。所有原始内容继续经过：

- 时间窗口过滤
- URL 规范化
- 历史 URL 排除
- 精确标题去重
- 现有语义去重
- 基础可信度、时效和官方来源排序

预处理后构建最多 36 条的 LLM 候选池。为了避免候选池在进入 LLM 前已经被单一来源占满，单一 `source_id` 最多进入 6 条。候选池仍按现有确定性分数排序；限制来源后再截取全局前 36 条。

如果不足 9 条有效候选，任务失败并保留上一期线上内容，不发布低质量空缺日报。

### 2. LLM 主编选择

所有候选在一次主编请求中统一比较，不再按 10 条一批逐条分析。LLM 只输出最终选择的 9 个候选及其精炼分析。

主编排序依次考虑：

1. 是否存在清晰、可验证的新变化，而不是泛泛讨论 AI。
2. 是否会影响产品、工程、商业或研究判断。
3. 是否来自一手或高可信来源。
4. 是否包含具体版本、数字、能力、开源发布、价格、政策或实证结论。
5. 是否值得目标读者今天投入时间。

以下内容应降权：

- 仅因研究中使用机器学习而与 AI 产品和产业判断关系很弱的垂直领域论文。
- 没有新事实、只有观点或营销措辞的内容。
- 与候选池中另一条描述同一事件但信息更少的内容。
- 只能产生“具有重要意义”“提供参考”之类通用价值判断的内容。

LLM 为每个入选候选指定一个 `editorial_lane`：

- `产品工程`
- `商业趋势`
- `前沿研究`

原有六类 `category` 继续保留，用于归档和分类导航；编辑方向用于本期配比校验，两者互不替代。

### 3. 精炼内容契约

新的 LLM 输出仍通过候选 `id` 与程序数据绑定，URL、来源和发布时间不能由 LLM 改写。每条分析包含：

- `title`：中文短标题，1–80 个字符。
- `editorial_lane`：三个编辑方向之一。
- `category`：现有六个分类之一。
- `summary`：发生了什么，20–160 个字符。
- `why_it_matters`：为什么值得关注，10–100 个字符。
- `tracking_signal`：建议行动或后续观察，5–80 个字符。
- `importance`：内部排序使用的 1–10 整数，不在页面上默认展示。
- `tags`：1–3 个短标签。
- `is_official` 和 `marketing_risk`：继续保留在数据中用于审计，不作为首页主要视觉元素。

LLM 可以提出基于候选事实的谨慎建议，但不能新增候选中不存在的事实、数字、发布日期或能力声明。

### 4. 确定性校验和一次修复

程序必须在接受 LLM 输出前验证：

- 输出是严格 JSON。
- 恰好包含 9 个唯一候选 ID。
- 所有 ID 都来自本次候选池。
- 三个编辑方向各 1–4 条。
- 单一 `source_id` 最多 3 条。
- 所有字段满足枚举、长度和数量限制。
- 输出不包含 API Key 或其他敏感值。

首次输出无效时，程序发起一次定向修复请求，明确指出违反的约束并附上脱敏后的无效输出。修复后仍不合格则终止本期发布，不能静默退回 20 条旧逻辑或放宽配比。

候选进入 LLM 前已有确定性去重；提示词还必须要求同一事件只保留信息最完整的一条。程序不把无法证明的语义重复检测冒充为硬校验。

## 数据兼容

新生成的报告使用 `schema_version: "1.1"`，并为每条 `NewsItem` 增加 `editorial_lane`。

站点构建器必须继续读取已有的 `1.0` 报告：

- 旧报告缺少 `editorial_lane` 时，根据现有分类提供兼容映射。
- 旧数据不回写、不批量迁移。
- 新报告只能写出 `1.1`。
- 历史归档和分类页面必须继续构建成功。

兼容映射只服务于旧报告展示，不参与新日报的 1–4 条编辑方向校验。

## 页面设计

### 首屏

首屏直接显示当天日期、一句简短定位和前三条重点标题。缩短现有大标题区域，删除占据整行的候选数、收录数和最后成功时间统计栏。

来源健康状态缩成一行次要信息，例如“14/15 个来源正常 · 更新于 08:23”，不与内容争夺视觉层级。

### 九条情报

页面只渲染一份 9 条列表：

- 前三条在同一列表中使用 `01`、`02`、`03` 和更强的视觉层级表示“今日重点”。
- 后六条继续编号 `04`–`09`。
- 不再生成单独且重复的“今日最重要”卡片组。
- 不再生成独立的“后续观察”侧栏；建议行动直接放在对应卡片内。

每张卡片默认展示：

1. 编辑方向、分类、来源和时间。
2. 短标题。
3. “变化”“影响”“行动”三段短句。
4. 原文链接。

首页移除原始标题、数字重要性、营销风险说明、官方状态、长标签列表、折叠研判详情、搜索框和页内分类按钮。现有顶部分类导航、日期归档和分类页继续保留。

### 历史页面

日期页使用与首页相同的精炼卡片。分类页和归档页继续工作，但不重复加入首页的搜索和筛选控制。

## 故障和发布策略

- 任一信息源失败仍记录 `degraded`，只要候选和最终约束仍满足即可发布。
- 候选不足 9 条、LLM 两次输出均无效或最终配比不合法时，本次生成失败。
- 生成失败不提交数据、不覆盖 GitHub Pages；上一期内容继续在线。
- Secrets 继续只通过 GitHub Actions 注入，日志和生成文件不得包含认证信息。
- 工作流现有 30 分钟任务上限和 LLM 120 秒单次请求超时保持不变。

## 测试要求

### 单元测试

- 候选池最多 36 条，单一来源最多 6 条，并保持确定性排序。
- 主编输出恰好 9 条，拒绝缺失、额外、重复和未知 ID。
- 拒绝任一编辑方向为 0 条或超过 4 条。
- 拒绝最终单一来源超过 3 条。
- 验证新字段长度、标签数量、敏感内容和一次修复行为。
- 验证旧 `1.0` 报告兼容读取和新 `1.1` 报告写出。

### 集成测试

- 离线端到端演示生成恰好 9 条。
- 首页和日期页每个新闻 ID 只出现一张卡片。
- 首页不存在旧搜索框、页内分类按钮、重复重点区和跟踪侧栏。
- 分类页、归档页、搜索索引、静态资源和基础路径继续有效。
- 桌面端和 390px 移动端无页面横向溢出。

### 生产验证

- 完整测试、覆盖率、Ruff、Secret 扫描、静态构建验证和工作流 lint 全部通过。
- 推送后精确提交的 CI 通过。
- 手动触发一次真实 Daily AI news。
- 真实报告恰好 9 条，三个编辑方向各 1–4 条，单一来源最多 3 条。
- GitHub Pages 首页显示新精炼结构，桌面和移动端交互及控制台状态正常。
- 机器人提交只能包含 `data/` 和 `content/` 中的生成文件。

## 验收标准

本次改造只有同时满足以下条件才算完成：

1. 线上最新一期恰好 9 条。
2. 三个编辑方向均有内容且各不超过 4 条。
3. 任一信息源不超过 3 条。
4. 每条只用“变化、影响、行动”三段短内容表达核心信息。
5. 首页没有前三条重复、长分析详情或大面积无效首屏。
6. 旧归档仍可访问。
7. 自动化测试和真实 GitHub Actions 生成、构建、部署全部成功。
