# AI 资讯「普通用户可读」编辑改造规格

## 背景与目标

当前日报仍会出现 SDK、框架、小版本修复和学术项目等技术细节。目标是把首页收敛为普通用户和业务人员每天可快速读完的 AI 产品与市场简报：只保留清晰、可验证、能影响产品选择、工作方式、价格或行业判断的变化。

## 已确认的产品决策

1. 采用严格的普通用户/业务价值口径（方案 B）。
2. 每天质量优先，通常发布 5–9 条；不合格内容不为凑数而加入。
3. 纯融资、估值和人事新闻不收录，除非明确影响产品、价格、用户或行业格局。
4. 保留三类栏目：产品与应用、商业与市场、平台与政策；不再设置前沿研究栏目。
5. 排除论文、科研项目、模型原理、基准测试、SDK/API、开发框架、代码工具细节和小版本更新。
6. 页面需要支持桌面、平板和手机响应式查看。

## 生成流程

### 候选预筛

现有采集、时间窗口、URL 规范化、历史去重和来源可信度排序继续保留。进入 LLM 前增加确定性编辑过滤：

- 标题、来源和摘要命中论文/学术、arXiv、SDK/API、框架、代码仓库、benchmark、模型训练细节、小版本修复等信号时拒绝；
- 纯融资、估值、人事和观点稿只有在候选事实明确影响产品、价格、用户或行业时保留；
- 保留官方产品公告、主流科技媒体、公司业务公告、政策监管和有具体用户影响的企业应用报道；
- 候选池不足时不以被排除类别补位。

### LLM 主编

LLM 在合格候选中统一比较、去重、选出最多 9 条，并优先选择：产品上线或重大能力变化、价格/可用范围变化、普通人可直接使用的新服务、企业实际采用、会改变市场规则的平台或政策变化。

每条输出严格包含：

- `title`：中文短标题，1–60 字；
- `lane`：`产品与应用`、`商业与市场`、`平台与政策` 之一；
- `summary`：发生了什么，20–100 字；
- `why_it_matters`：对用户或业务的直接影响，10–80 字；
- `source_url`：由候选 ID 绑定，LLM 不得改写；
- `importance`：内部排序用的 1–10 整数。

LLM 不得补充候选中不存在的数字、日期、能力和结论。程序负责 URL、来源、时间和候选事实绑定。

### 数量与失败策略

- 正常输出 5–9 条，不强制栏目均衡；无合格内容的栏目不显示。
- 少于 5 条时允许重选一次，但不放宽过滤标准；仍不足则按实际数量发布并记录警告。
- LLM 超时、JSON 无效或约束失败时沿用现有重试/修复机制；最终失败不覆盖上一期线上报告。
- 新报告写入 `schema_version: "1.2"`；站点继续兼容已有 1.0/1.1 历史报告。

## 页面改造

- 首页顶部仅显示日期、本期实际条数、来源健康状态和一句导读。
- 取消大面积编号、左侧分类栏、重复重点区、长分析字段、技术标签和无关统计。
- 每张卡片只展示栏目、标题、两段短文和来源链接；栏目按实际内容分组，不强制每组数量。
- 文章正文设置合理最大宽度，标题和摘要限制长度，减少首屏纵向噪音。
- 桌面端使用双列或宽单列卡片布局；平板自动收窄间距和字号；手机端单列、可读字号、链接保持触控尺寸，禁止横向溢出。
- 日期归档、分类页和基础路径继续可访问，并使用相同精炼卡片。

## 测试与验收

### 自动化测试

- 固定样本验证论文、SDK/API、框架、benchmark、小版本、纯融资和人事内容被拒绝。
- 验证产品发布、价格变化、用户功能、企业应用和实质政策变化可入选。
- 验证输出最多 9 条、正常不少于 5 条、ID 唯一、来源可追溯、字段长度合规。
- 验证 1.0/1.1 历史报告兼容读取和 1.2 新报告写出。
- 验证首页、日期页、分类页和归档页无重复内容；验证 390px、768px 和桌面宽度无横向溢出。

### 生产验收

- 完整测试、覆盖率、Ruff、Secret 扫描、静态构建和工作流检查通过。
- 手动触发一次 GitHub Actions，真实生成报告并部署 Pages。
- 正式网站检查最新内容符合过滤口径，实际条数为 5–9 条（极端情况下允许更少并有警告）。
- 在桌面、平板和手机视口检查首屏、卡片、导航、来源链接与历史页面。
